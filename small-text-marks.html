Dictionary dots at the smallest text size

The dots, their colour and their position are approved, so this page only looks at what happens when the reader text is at its smallest (0.7 times, which is 11.2 px, where px means screen pixels on a 16 px base). Every sample is a real 390 px wide phone paragraph shown 4 times larger so the marks can be seen. The word is Ember, and it is marked once as a saved copy (the paragraph it was saved from) and once as an ordinary copy.

1. Dot options at the smallest size

A. As it is today

The dots shrink with the text to under 1 px across but stay close together, so the row looks finer and busier than at 16 px.

B. Wider gaps at small sizes only

At the smallest size each dot stands apart and can be counted, but a short word gets only a few dots and the saved copy looks very sparse. At 16 px it matches option A.

C. Lighter dots at small sizes only

The dots keep their spacing but look softer and fainter, so they bother the eye less and are also harder to spot. At 16 px it matches option A.

D. A solid line and scaled dashes, the ReadEra way

The line is far heavier than the dots and stays easy to see at the smallest size, though it sits tight under the letters like heavy underlining. Other copies show one dash per letter, so the pattern stays tidy at any size.

3. What a release build of the phone app changes

A release build is the version of the app made for everyday use, rather than the one made for testing.

The reading code lives inside the app. Today the test build loads that code from the computer it was built on, so it only works while that computer is switched on and connected. A release build carries the code with it and works on its own.

It installs as a fresh app. The library and the saved words in the test build do not carry over, so books have to be added again and words saved again.

The test build stays installed beside it. Both apps sit on the phone at the same time and do not share anything.
